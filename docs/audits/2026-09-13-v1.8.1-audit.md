# GT Link Manager v1.8.1 audit

Date: September 13, 2026. Baseline: `v1.8.1`, commit `ead0ff0`.

The redirect and atomic counter foundations are suitable for v1.9.0, but detailed analytics should follow the correctness fixes below. Advanced analytics must have its own explicit opt-in and storage lifecycle. Existing click tracking consent does not authorize detailed analytics.

Scope: source review of redirect resolution, settings, database writes and caches, REST, admin actions, CSV, lifecycle, editor assets, and release packaging; focused runtime checks against the existing local release ZIP. This is an audit and implementation plan, not an implementation or production deployment.

## Findings to address before v1.9.0

### A1. P1: REST sanitization corrupts direct paths and regex patterns

Evidence: `includes/class-gt-link-rest-api.php:922-925` assigns `sanitize_title` to every incoming slug, before `sanitize_link_payload()` can select the mode-specific sanitizer.

Reproduced through WordPress REST dispatch with an administrator:

| Request | Actual stored slug | Impact |
| --- | --- | --- |
| Direct slug `docs/getting-started` | `docsgetting-started` | The intended path no longer resolves. |
| Regex slug `^old/(.*)$` | `old` | Anchors and capture groups disappear; the match can become broader and substitution breaks. |

Both requests returned HTTP 201. Fix route-level sanitization to preserve input for mode-aware validation, including PATCH requests whose mode comes from the existing record. Validate regex syntax before saving. Add real REST-dispatch regressions; directly calling the payload sanitizer would miss this bug.

### A2. P2: Redirect validation can perform blocking DNS before the response

Evidence: `includes/class-gt-link-redirect.php:155-158` calls `wp_http_validate_url()` for each resolved destination. The local WordPress 7.1 implementation calls `gethostbyname()` for a different hostname. This is also visible in the [official WordPress source](https://developer.wordpress.org/reference/functions/wp_http_validate_url/).

The slug object cache does not avoid this step. Resolver delays or failures can delay a redirect or turn it into a 404. No deliberately slow external DNS experiment was run.

Use a redirect-specific, non-network validator for the final destination after geo, regex, and filters. Retain explicit HTTP/HTTPS validation, host parsing, control-character protection, and the intended destination policy. Do not replace this with `wp_safe_redirect()` without supporting the plugin's intentional external destinations. Keep health/DNS checks, if desired, in explicit admin diagnostics.

### A3. P2: Click increments silently change the link's modification timestamp

Evidence: `includes/class-gt-link-activator.php:69` declares `updated_at ... ON UPDATE CURRENT_TIMESTAMP`. `includes/class-gt-link-db.php:282` updates the counter without preserving that column. Resetting a nonzero count has the same exposure.

In the isolated database, setting a fixture's `updated_at` to `2001-01-01 00:00:00` and incrementing its count changed the timestamp to the current time. This changes the apparent configuration edit date and indirectly retains the time of a counter update. The readme's unqualified “no timestamp” wording and privacy content need correction with the fix.

Preserve `updated_at` explicitly in increment/reset statements, or migrate to explicit configuration timestamps. Keep the atomic counter update and avoid cache invalidation per click. Do not fabricate historical edit timestamps during migration.

### A4. P2: The success hook fires when no click was recorded

Evidence: `includes/class-gt-link-redirect.php:254-262` ignores the boolean returned by `increment_clicks()` and always fires `gtlm_click_recorded`.

Reproduced using a nonexistent link ID: the database method returned false, but the success hook fired once. A deletion race or failed write can therefore produce a false success signal. Gate this hook on a successful counter write. Give advanced analytics its own event flow and success/failure signals instead of attaching its storage to this legacy counter hook.

### A5. P2: CSV round trips lose advanced redirect configuration

Evidence: `includes/class-gt-link-import.php:215-240` omits `link_mode`, `regex_replacement`, `priority`, and `is_active` from exports. `row_to_link_data()` at lines 456-505 sanitizes every slug as a standard slug and does not reconstruct those fields.

A direct link exported as `docs/getting-started` became a standard link when passed through the real import converter and database insert. New imports default to active; overwrite imports can reactivate an existing inactive link. Regex behavior cannot round-trip without the omitted fields.

Version the configuration export format and preserve these fields, while continuing to exclude click totals and analytics from configuration writes. Preserve existing values for missing columns in overwrite imports; use documented defaults only for new records. Keep analytics report export separate and streamed.

### A6. P2: Unexpected suffixes are attributed to a valid short link

Evidence: `includes/class-gt-link-redirect.php:403-411` keeps only the first path segment after the prefix. An actual HTTP request to `/go/audit-link/extra` returned the same 302 as `/go/audit-link` and reached counting.

The registered rewrite pattern accepts one segment, so the early resolver is looser than its declared route. Enforce the single-segment contract with optional trailing slash and query string. Check for installations relying on suffix aliases before releasing; preserve any needed aliases explicitly rather than silently assigning arbitrary paths to a link.

## Measurement semantics and performance constraints

- The existing count measures redirect requests, not verified human clicks. Actual HEAD, Googlebot, and prefetch requests each increased the total. POST increased it in a direct method probe. Preserve legacy semantics in v1.9.0; apply a separately documented eligibility policy to advanced analytics.
- `record_click()` invokes `fastcgi_finish_request()` where available. That can release the response before the database write, but it does not move processing into another worker. The PHP worker remains occupied. See the [PHP function documentation](https://www.php.net/manual/en/function.fastcgi-finish-request.php).
- Without FPM, calling `header()` is not a guarantee that the visitor has received a response. Injecting a 50 ms delay into the counter query produced a 58.22 ms TTFB in the local HTTP fixture. Any new analytics write on that path must be described and benchmarked as synchronous.
- The current bootstrap includes admin pages, importer, REST, and editor classes on public requests. Admin hooks/assets are guarded, but the admin constructor still creates its pages and importer before that guard. Lazy loading is a useful v1.9.0 optimization; no current latency saving is claimed.
- `GTLM_Settings::all()` remerges and sanitizes on each call. WordPress option caching means these are not automatically separate database reads. Resolve an analytics request configuration once; preserve existing filter semantics when optimizing settings.
- `flush_cache_group()` checks function existence rather than `wp_cache_supports('flush_group')`. This is a compatibility risk for third-party cache drop-ins, not a reproduced failure here. Use supported group invalidation or targeted keys and avoid global cache flushes for analytics changes. See [WordPress cache capability detection](https://developer.wordpress.org/reference/functions/wp_cache_supports/).

## Verified strengths to preserve

- Fresh click tracking defaults to off. Invoking the disabled collector performed zero queries and left the count unchanged in the fixture.
- Counting uses one atomic SQL increment; configuration edits do not include `total_clicks`. A stale configuration record did not overwrite a newer click count.
- REST PATCH preserved omitted destination/status fields and ignored a supplied `total_clicks` value. Anonymous link-list access returned 401.
- The HTTP fixture returned 302 for a standard link, 307 for a direct link, and 302 with correct capture substitution for a regex link created through the database layer. Missing, inactive, and trashed prefixed links returned 404.
- Redirect responses in these checks did not set cookies. Source review found admin/editor assets scoped to those contexts and no visitor tracking script or beacon.
- Geo detection uses existing request headers and is reached only for eligible geo links. The analytics design must not quietly turn on geo routing or add network geolocation.
- Existing trash retention protects older installs from retroactive deletion. Existing unlink/uninstall retention choices must remain intact.

## Validation and limits

Environment: isolated WordPress 7.1 fixture using copied release files, PHP 8.5.9 CLI/built-in HTTP server, MariaDB 12.3.2, no persistent object cache. Core files were read from an existing local Studio installation; its database and plugin files were not changed. All mutation and HTTP probes used a disposable local database and localhost.

| Check | Result |
| --- | --- |
| PHP syntax | All 16 plugin PHP files passed. |
| Admin JavaScript syntax | Passed `node --check assets/js/admin.js`. |
| PHPCS | 12 class-filename convention errors, zero warnings; not a clean lint pass. |
| Release ZIP | All 21 packaged files matched their checkout counterparts byte for byte. |
| ZIP SHA-256 | `e2e4552d2ed5362cba88a71e0d277e798b2c6dc594b142725f1718782d40ad5f` |
| Counter off, warm localhost requests | 2.654 ms median, 2.970 ms p95 TTFB. |
| Counter on, warm localhost requests | 2.881 ms median, 3.204 ms p95 TTFB. |

The timings are a small sequential smoke baseline: five warmups and 60 samples per condition, same-host target, no outbound DNS dependency, `SAVEQUERIES` on and WP-Cron disabled for repeatability. They are not production capacity evidence, an FPM benchmark, or a v1.9.0 result.

The repo has no checked-in automated behavior suite or pull-request test workflow. The release workflow packages on `release: published`, uses `npm install`, and rebuilds separately for WordPress.org. Add pre-release checks, use locked installs, and verify distribution parity before the next release. The current ZIP was inspected rather than rebuilt; browser/editor interaction, minimum supported PHP/WordPress versions, real FPM, persistent caches, multisite, load/concurrency, and production were not retested in this audit. WP-CLI emitted PHP 8.5 deprecations during fixture setup; these are tooling output, not evidence of a GTLM runtime failure.
